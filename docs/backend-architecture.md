# Backend module boundaries

The API is a modular monolith. The composition root in `apps/api/src/container.ts` connects module dependencies; `app.ts` owns HTTP middleware and mounts routers. The health module is the initial example: it receives readiness as a function and does not import MongoDB.

Add modules only when implementing their behavior. Business policy must not depend on Express, Mongoose or environment variables. Application actions depend on narrow ports where they need an external dependency; infrastructure implements those ports. HTTP adapters validate and map transport data. Cross-module interactions go through public contracts and the composition root; each module owns its writes. Run `pnpm check:boundaries` for automated API cycle, layer, unresolved-import and module public-contract checks. The documented shared-package resolver exception is checked by TypeScript.

The composition root gathers route declarations from `composition/dev1.ts` and `composition/dev2.ts`, checks duplicate method/path pairs, and registers them. Add each owned route through its composition file. This check detects exact pairs; overlapping parameterized patterns still require review. No fake authentication or domain ports are wired into production.

Authorization progress: grouped admin/customer/rider registries, role CRUD and nine staff endpoints are implemented. `identity/administration.public.ts` composes F02 independently of mock OTP whenever a JWT key is configured; mock identities are accepted only by development composition. Current identity, role and scope are read on each request. Production password login, restricted credential transitions and TOTP enrolment are composed separately from development OTP. Enforcement on other business modules remains a separate integration task.

`requirePermission` is the reusable HTTP guard exported by the access module. It receives a current-actor resolver, required permission, target-scope resolver and the protected handler. Missing identity returns a safe 401; denied permission/scope returns 403. Actor-resolution failures pass to safe global error handling without executing the protected handler. The development permission endpoint now uses this guard instead of inline enforcement.

Future routes must explicitly opt into the guard and supply a trusted actor resolver. For resource-ID routes, determine warehouse ownership from the authoritative record, not a client-supplied warehouse query/body field. List routes must also apply server-side scope filters; a guard does not automatically filter query results. Staff session validation also enforces pending password/2FA requirements; other modules must explicitly use trusted current-actor resolution.

Role and staff mutations share transactions with audit persistence. Staff mutations lock the current session/user/role and the target user/role; forced logout and credential resets revoke all target sessions in the same transaction. Staff lists filter whole accounts by scope and batch role lookups. User creation and staff assignment touch the assigned role revision to conflict with deletion; future assignment paths must use this protocol. Passwords use versioned salted scrypt. Reset-2FA removes credentials, marks re-enrolment required and revokes sessions; Staff F01 enforces enrolment/password-change states before issuing normal sessions.
